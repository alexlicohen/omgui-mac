## Confirmed (ranked HIGH → LOW)

### HIGH

**H1 · `Vendor/libomapi/src/omapi-main.c:125-142`** (with `omapi-devicefinder-mac.c:753-760`, `omapi-internal.c:223-226`) — **C3 is not closed on the quit path; the UAF moved rather than went away.** The C3 patch put an *unbounded* `OmDownloadCancelJoin` inside the IOKit removal callback, but `OmDeviceDiscoveryStop`'s wait is *bounded* (100 × 50 ms) and detaches on timeout. Unplug mid-download then Cmd-Q: the discovery thread is blocked in `thread_join` inside the callback so `CFRunLoopStop` is never processed, `OmShutdown` gives up after ~5 s, calls `OmDownloadCancelJoin` again (handle already taken → joins nothing), and `free(record->state)` runs under two live threads. Download thread then dereferences the freed `deviceState` and `fclose()`s a freed `FILE*`; the detached discovery thread writes `deviceStatus = OM_DEVICE_REMOVED` into freed memory and calls `om.deviceCallback`; `mutex_destroy(&om.downloadMutex)` at :142 races a live `mutex_lock`.
*Fix:* on the `!finished` branch, set a flag that makes `OmShutdown` skip both `free(record->state)` and both `mutex_destroy` calls (leak on a wedged quit). Or take the download handle out of the removal callback entirely — signal `downloadCancel` there, do the one authoritative join in `OmShutdown` after the discovery thread has actually been joined.
*Votes:* 2/0/0.

**H2 · `Vendor/libomapi/src/omapi-internal.c:223` (join) vs `:226` (status store)** — **Cancel-before-REMOVED opens a start race and blocks the discovery run loop.** The C3 reorder put the join *ahead* of the status store (upstream did the reverse). During the join the device still reads `OM_DEVICE_CONNECTED`, so `OmBeginDownloading`'s guard (`omapi-download.c:259`) passes: `downloadCancel = 1` is set *outside* `om.downloadMutex` (`download.c:441`), the main thread clears it and creates a fresh thread, and `OmDownloadTakeThread` hands the discovery thread the **new** handle with cancel cleared — so the run-loop thread now waits for a full download off a disappearing volume. For that entire time no attach/detach events are delivered and the UI keeps showing the device connected. (Subsumes the separately-reported LOW "device removal joins the download thread synchronously on the IOKit notification thread", `omapi-internal.c:218-223`, 2/0/0 — same root, same fix.)
*Fix:* store `deviceStatus = OM_DEVICE_REMOVED` **first** (it is `_Atomic`, so it closes the `OmBeginDownloading` window immediately), then join. Set `downloadCancel = 1` *inside* `om.downloadMutex`. Best: move the join off the run-loop thread entirely.
*Votes:* 2/0/0.

**H3 · `Vendor/libomapi/src/omapi-main.c:134`** — **`OmShutdown`'s unconditional cancel+join is an unbounded block on the main thread.** Reached from `@MainActor AppModel.shutdown()` (`Sources/OmGui/AppModel.swift:187`). Device yanked mid-download before IOKit delivers `kIOMessageServiceIsTerminated`, user hits Cmd-Q: the download thread is parked in `fread()` on the vanished volume and the main thread blocks until the kernel times the read out — directly after `OmDeviceDiscoveryStop`'s own up-to-5 s main-thread wait. Upstream never joined here; this is a newly introduced blocking path.
*Fix:* bound it the way C17 bounds the discovery join — `downloadFinished` flag + condvar set in `OmDownloadThread`'s epilogue, `pthread_cond_timedwait` with a fixed budget, leak the `OmDeviceState` on timeout (Darwin has no `pthread_timedjoin_np`). Also invalidate `downloadSource` before the join so the blocked `fread()` returns.
*Votes:* 2/0/0.

**H4 · `Vendor/libomapi/src/omapi-devicefinder-mac.c:755-759`** — **The detach path trades a hang for undefined behaviour.** On stop-loop expiry, `pthread_detach` + early return, without clearing `gRunLoop`/`gNotifyPort`/`gAddedIter` and without telling `OmShutdown` the thread is alive. `OmShutdown` then frees the states and destroys the mutexes. A discovery thread stuck >5 s in `getUSBStringDescriptor`'s `DeviceRequest` or `mountPathForBsdName`'s DiskArbitration call subsequently walks freed records, locks a destroyed mutex, and invokes `om.deviceCallback` — which does `Unmanaged<LibOmapiBackend>.fromOpaque(...).takeUnretainedValue()` (`LibOmapiBackend.swift:50-63`) while `shutdown()` only nulls the callbacks *after* `OmShutdown` returns (:77-80).
*Fix:* before `pthread_detach`, null the three callbacks and set a `gDiscoveryDetached` flag exported to `omapi-main.c`; have `OmShutdown` skip the frees and both `mutex_destroy` calls when set. Null `gRunLoop`; leave `gNotifyPort`/`gAddedIter` owned by the orphan.
*Votes:* 2/0/0.

**M1 · `Vendor/libomapi/src/omapi-devicefinder-mac.c:687-688`** — `gStartMutex`/`gStartCond` are unconditionally re-`init`'d on every start on never-destroyed statics, and `gStarted`/`gFinished`/`gThreadValid` are single global slots. After an H4 detach + a backend restart (`OmApi.replaceBackend` + `startup()`, `OmApi.swift:87-97`), the orphan runs `OmDiscoverySignal(1,1)` on the **new** cycle's globals: (a) the new start's `while (!gStarted && !gFinished)` exits immediately, returning before the run loop is up — reinstating the race the 200 ms usleep papered over; (b) the next `Stop` sees `gFinished` already set, skips every `CFRunLoopStop`, and joins a thread whose run loop is still running — a permanent hang, the exact bug C17 exists to remove.
